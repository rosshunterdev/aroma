# Finished Aroma Coffee Works website

Status: approved

## Problem Statement

Aroma's public root is currently a completed temporary under-construction page. The preserved multi-page site is an early draft based on an outdated café-only product framing and an earlier brown/cream/sage visual direction. It contains unresolved content, broken draft references and a Food/Coffee/Tea carousel that no longer matches the approved direction.

Visitors need a finished site that quickly communicates Aroma as one warm, local Miramar brand with two related offerings: a slightly primary, casual Café and a clearly visible, somewhat more refined Restaurant. They must be able to understand each atmosphere, reach the appropriate menu, plan a visit and follow the confirmed booking route without ambiguity. The site must not publish provisional client facts as truth.

Before production design begins, Phillip also needs three genuinely distinct, equally mature visual concepts based on the same approved product structure so he can select one coherent direction.

## Solution

Create a finished, restrained five-page website with top-level destinations for Home, Café, Restaurant, About and Visit. The Aroma wordmark links home. Café and Restaurant each have a focused page containing their atmosphere, accessible web menu and relevant primary action; there is no ambiguous generic Menu destination.

The homepage is slightly Café-led while giving Restaurant deliberate visibility. It uses a strong, mostly static hero led by candid venue-and-people photography, clear Café and Restaurant paths, a small set of selected highlights and concise Visit information. The former Food/Coffee/Tea carousel is removed.

One shared Aroma identity governs the whole site. The Café expression is casual, warm and coffee-oriented. The Restaurant uses a restrained combination of evening photography and lighting, refined typography and spacing, deeper variants of the shared palette and slightly more formal language. It remains immediately recognisable as Aroma.

The visual brief is minimalist and Kiwi-oriented: green primary, red secondary and white background, with an approachable local-neighbourhood feeling rather than literal New Zealand motifs. Client-approved Vietnamese highlights receive only a small red label or accent; Vietnamese styling does not become the overall theme.

Work proceeds through three blocking phases within this specification:

1. **Phase A — Concept design:** Produce three concept directions—Refined minimal, Warm neighbourhood and Day-to-night Aroma—using the same structure and clearly marked placeholder material where necessary. Phillip selects one overall direction.
2. **Phase B — Selected-direction refinement:** Refine the selected direction and resolve its design details. This phase is blocked by Phillip's concept selection.
3. **Phase C — Production implementation:** Build only the approved direction when the client facts and assets required for production are sufficiently confirmed. This phase is blocked by approval of the refined direction and by the production dependencies identified below. The temporary under-construction page remains operationally separate until an intentional final-site release replaces it.

25. As a visitor planning a trip, I want Café and Restaurant hours shown separately, so that I do not apply one offering's schedule to the other.
26. As a visitor planning a trip, I want the confirmed street address and an Open in Google Maps link, so that I can navigate using my preferred maps application.
27. As a visitor, I want confirmed phone and email details in one predictable place, so that I can contact Aroma confidently.
28. As a visitor with access needs, I want any client-supplied parking, transport or access information, so that I can plan my arrival.
29. As a local-search visitor, I want search results and page metadata to describe the relevant offering accurately, so that I land on useful information.
30. As a search-engine user, I want Aroma's address, hours and contact details to be consistent, so that I am not misled by conflicting information.
31. As a keyboard user, I want every navigation element, menu link and primary action to be operable with a visible focus state, so that I can use the complete site.
32. As a low-vision visitor, I want sufficient contrast, zoom and reflow support, so that content remains legible without horizontal scrolling.
33. As a motion-sensitive visitor, I want nonessential motion reduced or absent, so that the experience remains comfortable.
34. As a screen-reader user, I want semantic headings, landmarks, link names and meaningful image alternatives, so that each page is understandable without its visual presentation.
35. As a visitor on a slow mobile connection, I want a fast, restrained site, so that large photography and fonts do not block the primary journeys.
36. As Phillip, I want three distinct concepts built on the same product structure, so that I can compare brand directions rather than incompatible site plans.
37. As Phillip, I want placeholders and provisional facts clearly labelled in concepts, so that I do not mistake them for approved launch content.

## Implementation Decisions

- Preserve the existing static HTML, CSS and minimal vanilla-JavaScript architecture as the approved planning default. Hosting/domain/maintenance research does not block ticket creation or work that stays within that architecture. The research and owner approval are required before changing the architecture, selecting production hosting/deployment ownership, introducing a CMS or materially different maintenance model, or releasing to production.
- Treat the temporary under-construction page as a separate accepted artifact. Concept work and final-site implementation must not repurpose or incrementally redesign it. Replacing the public root is a deliberate release step after final-site acceptance.
- Use five top-level destinations: Home, Café, Restaurant, About and Visit. The Aroma wordmark acts as the Home link. Do not add a generic Menu item.
- Give Café and Restaurant dedicated pages. Each offering page combines atmosphere, its own accessible web menu and its relevant primary action rather than splitting those journeys across extra pages.
- Keep offering pages simple: direct hierarchy, no nested navigation requirement, no menu filtering and no carousel. Use category jump links only when content length justifies them.
- Keep the homepage to four core sections: a Café-led photographic hero, clear Café/Restaurant paths, a small set of selected highlights and concise Visit information.
- Remove the Food/Coffee/Tea carousel from the final product. No carousel behavior or autoplay migrates from the early draft.
- Use one Aroma design system across both offerings. Establish shared colour, typography, spacing, layout, interaction and component rules before applying a restrained Restaurant variation.
- Use green as the primary colour, red as the secondary accent and white as the base background. Final colour values are chosen during the selected design direction and must meet WCAG 2.2 AA contrast requirements.
- Interpret Kiwi-oriented as approachable, unpretentious and local. Do not use flags, fern motifs or other literal national shorthand merely to satisfy the brief.
- Make the Café mood casual, warm and coffee-oriented. Make the Restaurant mood more evening, refined, professional and considered using a controlled combination of photography/lighting, typography/spacing, deeper shared colours and language—not a separate brand skin. A specifically romantic mood is not required.
- Use a strong venue-and-people photograph as the homepage's dominant atmospheric element. Its intended mood is candid, local, community-oriented, warm and intimate. Final assets require Phillip's approval and appropriate usage permission.
- Mark approved Vietnamese highlights with a small red accent or text label. The label must communicate meaning without colour alone. Do not apply ornamental Vietnamese theming across the interface.
- Make About people-, place- and community-led. Include Vietnamese background and culinary influence only through Phillip-supplied or approved factual story content.
- Render both menus as semantic web content with categories, item names, descriptions where approved and prices where confirmed. A PDF may be offered only as a maintained secondary format.
- Make Visit the shared utility destination. It contains separately labelled confirmed Café and Restaurant hours, confirmed address, Open in Google Maps link, confirmed contact details, useful client-supplied access information and the confirmed Restaurant booking method.
- Repeat the confirmed booking action prominently on the Restaurant page. Do not assume phone, email, an external service or a reservation form until Phillip confirms the method.
- Do not embed an interactive map by default. The address and external Maps link are the functional journey.
- Reserve an optional place for a future colour-matched Miramar illustration, but do not design or ship it until a visual direction is selected and accuracy, accessibility and source-data licensing are resolved.
- Use warm, concise and straightforward copy. Keep it locally grounded without forced Kiwi phrasing, exaggerated claims, generic luxury language or long brand manifestos. Restaurant wording may be slightly more polished while retaining Aroma's voice.
- Create three separate concept artifacts for Phillip: Refined minimal, Warm neighbourhood and Day-to-night Aroma. They must use identical product scope and comparable content states, be equally mature and differ materially in atmosphere and brand expression.
- Use existing Option A/B, the early draft, Park Kitchen and other handoff materials as evidence only. Do not treat their exact layouts, fonts, tokens, copy, contact facts or components as approved requirements.
- Mark concept-only pages clearly as review material and prevent them from being indexed. Placeholder copy, content slots and representative temporary imagery are permitted only when unmistakably labelled.
- Ask Phillip to choose one overall concept before refinement. Borrow elements from other concepts only selectively and only when they preserve the chosen direction's coherence.
- Treat direct client confirmation as the highest content authority. Preserve unresolved facts as named dependencies and never convert plausible values, old-site content, public listings or comp copy into confirmed production content.
- Keep metadata and structured data offering-specific and factually conservative. Do not claim the Restaurant is available until its status, name, hours and launch timing are confirmed.
- Meet WCAG 2.2 AA at launch. Accessibility is part of design and implementation acceptance, not a later audit-only enhancement.
- Optimise large images, constrain responsive image delivery and avoid unnecessary scripts, embeds and third-party services. Performance budgets should be finalised during implementation planning using representative mobile conditions.
- Research hosting/domain ownership and maintenance workflow during the programme. The recommendation must address cost, account ownership, deployment, rollback/recovery, handover and expected update frequency.
- Complete and approve that research before changing the static architecture, selecting production hosting/deployment ownership, introducing a CMS or materially different maintenance model, or releasing to production. Do not allow an unapproved architecture, CMS, hosting or maintenance choice to emerge incidentally during implementation.

## Testing Decisions

- Use one primary behavioural test seam: the fully rendered static site served over HTTP and exercised through observable browser journeys. Tests should verify what visitors can see, reach and operate rather than private markup organization or CSS implementation details.
- Supplement that seam with narrow static or automated checks for content provenance, metadata and structured data, internal routes and assets, accessibility automation, and other contracts that browser journeys alone diagnose poorly. Do not couple tests to internal markup or CSS organization unless a genuine reusable behaviour seam requires it.
- Concept-phase checks cover all three review options at representative desktop and mobile widths: identical required structure, clear review labelling, no indexing, no horizontal overflow, working option navigation and no unlabelled provisional facts.
- Final-site journey checks cover: wordmark-to-Home navigation; every top-level destination; Home-to-Café and Home-to-Restaurant paths; Café menu discovery; Restaurant menu discovery; Restaurant booking action; Visit directions; and return navigation.
- Menu checks verify semantic, visible web content; correct category navigation where present; keyboard reachability; no PDF-only dependency; and no filtering/carousel requirement.
- Content-provenance checks compare every production business fact against the approved content record. Tests must fail or launch must remain blocked when required client facts are unresolved, rather than accepting placeholder text.
- Accessibility verification combines automated WCAG checks with manual keyboard navigation, visible-focus review, heading/landmark inspection, link-name review, image-alternative review, 200% zoom/reflow checks, reduced-motion behavior and representative screen-reader journeys.
- Responsive checks cover at least a small mobile width, a larger mobile/tablet width and desktop. They verify usable tap targets, readable menu layouts, compact navigation, early primary actions and absence of horizontal scrolling.
- Visual checks confirm that Café and Restaurant remain recognisably one brand while their agreed tonal difference is perceptible. This requires human review; snapshot differences alone cannot establish brand intent.
- Performance checks use representative production assets and mobile conditions. Verify image sizing/compression, font behavior, script weight, loading stability and absence of unnecessary third-party requests. Set numeric budgets before implementation tickets are approved.
- SEO checks verify unique and accurate titles/descriptions, canonical behavior, crawl/index rules, consistent confirmed local facts, meaningful link structure and structured data that does not overstate Restaurant availability.
- Link and asset checks verify no broken internal routes, missing local assets, malformed phone/email/map links or references back into concept-only pages.
- Privacy/security checks verify that any analytics, embeds, forms or external booking services introduced after client confirmation receive an explicit privacy/legal assessment before launch.
- Existing browser-check work on the redesign branch is useful prior art for viewport, heading, overflow, focus, noindex and content-slot checks. Reuse its behavioral ideas, not its comp-specific selectors or provisional facts.
- A good test should remain valid when internal HTML/CSS organization changes, should identify the visitor-visible contract it protects and should not lock the selected design to pixel-perfect implementation details unless a reviewed visual artifact explicitly requires them.

## Out of Scope

- Redesigning or replacing the accepted temporary under-construction page before final-site release.
- Implementing the production site during specification or concept selection.
- Treating all three design concepts as production sites; only one direction proceeds after Phillip's selection.
- Carrying forward the Food/Coffee/Tea carousel, autoplay behavior or homepage category tabs.
- A generic shared Menu destination, menu filtering or a PDF-only menu.
- Online ordering, unless Phillip explicitly changes the confirmed direction in a later decision.
- Social feeds, newsletter signup, events, vouchers, loyalty features, elaborate animation and other unvalidated integrations.
- Literal New Zealand theming or a site-wide Vietnamese visual theme.
- An interactive map embed by default.
- Designing the optional Miramar illustration before concept selection and research.
- Inventing Restaurant menu, hours, launch timing, booking method or availability.
- Inventing or silently selecting phone, email, Café hours, prices, social links, story claims, highlight items or photography.
- Selecting final hosting, deployment ownership, CMS or maintenance tooling without the required research and approval.
- Creating implementation tickets before this specification is approved.

## Further Notes

### Content dependencies

**Concept-review dependencies:** The three concepts may use clearly labelled representative placeholders for unresolved copy, photography and operational facts when exact values are not necessary to judge the design. Concept review is blocked only by missing information that would materially change the information architecture, the relationship between Café and Restaurant, or the concept being evaluated. If Restaurant naming/status or another unresolved fact would change those foundations, obtain it before presenting the affected concept.

Confirmed phone, exact prices, final hours, final Restaurant booking method and comparable production details do not block concept review when they can be represented honestly as labelled placeholders.

**Production dependencies:** Production implementation and release depend on Phillip confirming or approving, as applicable:

- Public trading name and whether the Restaurant uses the same customer-facing name.
- Café and Restaurant menus, categories, descriptions, prices and availability.
- Café and Restaurant days and hours.
- Restaurant launch date/status and whether it may be promoted before opening.
- Restaurant booking method and approved booking copy.
- Current phone number and email address.
- About story, people/community details and Vietnamese-background narrative.
- Which items qualify as Vietnamese highlights and the approved label/descriptions.
- Hero, venue, people, Café, Restaurant and menu photography, including permission to use it.
- Social links and any parking, transport or access details intended for publication.
- Any existing brand colours or assets that must constrain the selected direction.

The only confirmed operating location currently available for production use is 128D Park Road, Miramar. All other unresolved values remain placeholders or launch blockers according to their usage.

### Programme research and release gates

- Recommend the lowest-maintenance hosting, domain and deployment ownership model.
- Compare developer-managed, client-editable and hybrid maintenance models against real update frequency.
- Decide how an unlaunched Restaurant is represented in pages, metadata and structured data.
- Set measurable performance budgets using the selected design and real assets.
- Decide whether analytics, forms, booking services or other integrations are needed and complete the resulting privacy/legal assessment.
- After concept selection, decide whether the optional Miramar illustration is valuable and legally/technically supportable.

This research does not block ticket creation or static-architecture planning. It must be complete before any architecture/CMS/maintenance-model change, before production hosting/deployment ownership is selected, and before final production release.
